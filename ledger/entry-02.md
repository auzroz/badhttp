**Research first (4 agents + a cross-check, all live sources).** x402 is at v2 (CAIP-2 networks, `PAYMENT-REQUIRED` / `PAYMENT-SIGNATURE` / `PAYMENT-RESPONSE` headers carrying base64 JSON); the repo moved to `x402-foundation/x402`; `@x402/core` 2.23.0 is the reference. I took the wire shapes from the SDK source, not memory. USDC's EIP-712 domain differs per network — read from chain: Base mainnet `name "USD Coin"`, Base Sepolia `name "USDC"`, both `version "2"` (OpenX402's `/supported` gets Sepolia wrong). Facilitator survey, credential-free on both Base networks: **xpay** (zero fee, no cap, verify 100/min, settle 50/min; young, single signer), **Mogami** (no fee, AGPL server), **PayAI** (oldest, biggest, but 1,000 *lifetime* free settlements per receiving wallet, shared-IP pool caveat, then an API key), **Heurist** (mainnet only, ~3 s verify). Coinbase's `x402.org/facilitator` is Sepolia-only without CDP keys. OpenX402 needs the payTo address registered (5 USDC + a wallet signature): not possible for a receive-only project. Daydreams and thirdweb need bearer tokens.

**Built.** `src/x402.js` (v0.2.0): `/402/pay` is a real x402 v2 paywall (default Base Sepolia, `?network=base` for mainnet, `?amount=` 0.001–1.00 USD, default 0.01, payTo = the receive address, facilitator chain with failover: mainnet xpay → Mogami → PayAI → Heurist; Sepolia Coinbase → xpay → Mogami → PayAI; a facilitator-side rejection like `address_not_registered` also fails over). Everything else in the range never contacts a facilitator and never settles: `/402/never`, `/402/reject?reason=`, `/402/slow?seconds=`, `/402/crash`, `/402/bad-receipt`, `/402/overpriced` (asks for 1,000,000 USDC), `/402/wrong-network` (`eip155:424242`), and `/402/broken/{10 flavors}` of malformed 402s. Each scenario defaults to Sepolia so an unattended client can only ever sign testnet authorizations unless it asks for mainnet. Home page section, `/402` JSON index, OpenAPI, README, 17 new smoke checks (none send a payment), `scripts/x402-pay.mjs` (official-client payer).

**Verified with the official client (`@x402/fetch` + `@x402/evm` 2.23.0, throwaway payer).** Our 402 parses; the client signs; our server matches `accepted` against its own requirements and calls the facilitator; every facilitator in both chains verifies the real signature and rejects only for balance (`insufficient_funds` / `invalid_exact_evm_insufficient_balance`); failover through a dead host and OpenX402's policy rejection lands on Mogami. Scenario behaviour against the real client: `never` → client stops after one retry; `bad-receipt` → the official client passes the 200 through (its receipt decode is swallowed; a caller that decodes `PAYMENT-RESPONSE` itself throws); `overpriced` → refused by the client's default $1 `maxAmountPerPayment`; `wrong-network` → refused; `broken/no-accepts` → the official client crashes with a TypeError (worth reporting upstream); `broken/no-resource` → the official client signs anyway (resource is optional to it). **Not verified: settlement itself.** The throwaway payer holds no USDC; Circle's faucet is behind reCAPTCHA and the API faucets need a developer account, i.e. a human. The catalogue says so in one sentence.

**Reviewed.** 5 lenses, every finding independently refuted-or-confirmed: 21 confirmed, all fixed before deploy. The ones that mattered: a facilitator's `settlement_pending` (transfer broadcast, receipt wait timed out) was answered with a fresh 402 and `charged: false` — now a 202 with the receipt header and "do not pay again"; an HTTP-400 verdict from a facilitator (x402.rs style) was treated as "try the next one" — verdicts are now body-based and a 4xx without a verdict is terminal, so junk costs one call, not four; the inner EIP-3009 payload is now shape-checked (signature, recipient = payTo, value = amount, expiry) before any facilitator sees it; `nonce_already_used` now reports "probably charged by an earlier attempt" instead of `charged: false`; `?reason`/`?seconds` are validated before the first 402 so a client never signs against a URL that then 400s; `resource.url` is rebuilt from known params so a junk query cannot inflate the header past Node's 16 KB limit; HEAD never settles and other methods get a 405; Workers invocation logs are off so discarded signatures are not retained; the lede no longer says "free"; the facilitators are named in `GET /402`; "verified" claims are generated from one `VERIFIED` object.
