What was wrong with the mitigation as it stood: it keyed on one string the sender controls, and the sender has been seen tuning its user-agent set during the flood (#33: a 33-string tier retired, an Android cohort added). A change of string would have put the whole flood back on the Worker at $2.70 a day at today's volume, and the detection latency is the session cadence (#33: seven days unnoticed) — ten days of that is $27, forty percent of what remains of the year's cap. Two changes, both on the zone before anything else was touched (the Worker cannot defend itself; #33 rule (a)):

- **Rule 1 made case-insensitive:** `(http.request.uri.path eq "/compress/bomb" and lower(http.user_agent) contains "mozilla/")`. `lower()` is accepted on the Free plan; an upper-case `MOZILLA/` and a lower-case `mozilla/` both get the 403 now (both verified).
- **Rule 2, new, independent of the user agent:** `(http.request.uri.path eq "/compress/bomb" and any(http.request.uri.args.names[*] == "size") and not any(http.request.uri.args["size"][*] in {"1" "2" "3" "4" "5" "6" "7" "8"}) and not any(http.request.headers["x-badhttp-bomb"][*] == "accept"))` → block. Any explicit `?size=` other than the eight values at or below the default needs the request header `x-badhttp-bomb: accept`. The flood's URL is `?size=32`; a change of browser string alone now lands on this rule, unbilled. The default bomb (8 MiB, 24,491 bytes on the wire) and `?size=` 1–8 are untouched, and nothing in this project requested a size above 1 (smoke uses `?size=1`; the compress witness harness fetches the default; no corpus row carries `?size=`), and nothing outside it had asked for the bomb at all (above). This is the second rung of #33's own ladder ("an opt-in header above 8 MiB"), pulled one rung early because the flood doubled and the detection latency did not shrink.

Verified live at 21:10 UTC for fifteen request shapes (seventeen by the deploy, after the review), all with `Accept-Encoding: gzip`: no `?size=` → 200 from the Worker; `?size=4`, `?size=8` → 200; `?size=32` without the header → 403 from the edge (no `x-badhttp-version`); `?size=32` with it → 200 (the 97,729-byte member); `?size=032`, `?size=%33%32`, `?size=abc`, `?size=` (empty) and `?size=32` with a wrong header value (`yes`) → 403 at the edge; `?size=33` with the header → 400 from the Worker (its own validation, as before); `?nosize=1` → 200; `?size=1&size=32` → 200 (the edge's allow-set matches the first value and the Worker reads the first value: 1 MiB); the upper-case and lower-case `Mozilla/` user agents → 403 at the edge.
