**The dimension the first two families did not have, and how the design critic changed it.** An HTTP client does nothing with a 401 unless the caller configured credentials through some mechanism, and clients differ in which exist. My first grid handed each client "its Basic mechanism" everywhere Basic-shaped, "its Digest mechanism" on the Digest flavors, and named the kinds `basic-preemptive` / `digest-challenge` / `negotiate`. A critic agent, reading the design against `docs/spec-clients.md` and the crosshost precedent, returned 24 findings, and the five that changed the harness are worth the record: (1) six of eight clients never *see* the challenge on the challenge-parser flavors (bare-scheme, token68, case, quoted, unknown-scheme, multi), because a first-request Basic header gets its 200 before any parser runs — so those flavors now get each client's **challenge-driven** mechanism where one exists (curl `--anyauth`, urllib's handler; on `multi` the Python Digest objects, which must parse the two-challenge header to answer), and rows that still had to be handed a Basic option say the challenge was never observed; (2) the kind names asserted the outcome ("preemptive") as configuration — they now name **what was configured** (`basic-auth`, `basic-header`, `basic-handler`, `digest-handler`, `any-handler`, `bearer-auth`, `bearer-header`, `no-mechanism`) and whether credentials went out first is read from the rows; (3) a request count alone cannot say which request carried credentials, so every harness now records **per request the client sent: its status and whether Authorization / Proxy-Authorization was present** (never a value), from which `credentialed_requests`, `sent_credentials_first` and `statuses_seen` are derived; (4) the proxy rows were configured with *origin* credentials that `/auth/proxy` never reads, so they must say so and the finding must not read as "no client leaks proxy credentials" — it now says what was and was not observed; (5) disagreement keyed on the result alone would count the harness's own grid as clients disagreeing, so `distinct_answers` now counts distinct answers **among clients configured the same way**. Also from the critic: the oracle body is kept by allowlist (the identity keys `user`/`token` and the constant prose are dropped), the outcome classifier is exhaustive and throws on any shape it does not name, `challenge_seen` is *validated* rather than scrubbed (it must start with a scheme this server emits and carry no `response=`/`username=`/`uri=`/`cnonce=`/`nc=`), the parser refuses a `did-not-land` row or a partial grid outright, and a fixed needle set — both base64 encodings of the documented Basic credentials, the raw and URL-encoded values, the token, a `Proxy-Authorization:` line, a Digest `response=` — must appear in no row string and not in the committed run log.

**What the eight clients did on 2026-09-18 (every claim is a row; the twelve findings on `/auth` and `/clients` are computed from them).** 144 observations, 0 retries: 98 authenticated, 44 refused, 2 client-raised. Only **urllib** waits for a challenge; every other client's Basic option sends on the first request, so on `none` (a 401 with no challenge at all) seven authenticated and urllib could not. **Go net/http, Node fetch and urllib3 have no Digest mechanism** and no challenge handling of any kind; the other five completed MD5 and SHA-256 in two requests. On `stale`, **curl and urllib** retried on `stale=true` and reached generations 2; **requests, httpx and aiohttp** handed the stale 401 back after the one retry each allows per call — none of the three reads the parameter, and all three would complete the dance on a reused auth object. On `multi`, the two clients that choose (curl `--anyauth`, urllib with both handlers) both chose Digest, and the three Python Digest objects parsed the two-challenge header correctly. `always-401`: one credentialed attempt everywhere, no loops. `utf8`: **curl, Go, urllib and httpx sent the é as UTF-8; requests, urllib3 and aiohttp as Latin-1** (requests' and urllib3's encoders default to latin-1 "for backward compatibility"; `aiohttp.BasicAuth` defaults to latin1 while its newer `encode_basic_auth()` defaults to UTF-8); Node's row is harness-encoded and says so. `proxy`: no client answered an origin's 407 with the origin credentials; seven handed it back after one request and **Node fetch rejected the call with `TypeError: fetch failed`** — the Fetch standard turns a 407 into a network error and undici applies that outside a browser, so the 407 never reaches the caller. On the parser flavors, **curl answered the realm-less `bare-scheme` challenge and urllib declined it** (its Basic handler's regex requires `realm=`), and on `unknown-scheme` urllib raised `ValueError` after the 401 had already arrived while curl returned it. `redirect`: the credential followed for all eight (302 then 200 with credentials on both requests, except urllib's 302 → 401 → 200). Within-kind disagreement — two clients configured the same way receiving different answers — exists on exactly two flavors: `stale` and `utf8`.
