- **Method, the part that is new.** Every client is a CLI or a driver, so one orchestrator drives the whole roster; the clients are observed through a **local recording reverse proxy** (`scripts/range-witness/recorder.mjs`): the client is pointed at a loopback `http://` URL, the recorder forwards each request verbatim to badhttp.dev over TLS (HTTP/1.1) and returns the response verbatim (status, headers, body, Content-Length preserved), and writes one exchange record per request — so the rows list exactly what each client asked for (`Range`, `If-Range`, HEAD-first probes, no-Range GETs) and exactly what it was given, without a per-library hook. No loopback literal reaches a row (the parser refuses one). What this gives up, and the index says so: TLS/ALPN/HTTP/2 behaviour. The reference for each flavor is **where RFC 9110 places the bytes the raw-wire control received** (a 200 replaces the file; a 206 puts its body at the offset its Content-Range names; a 206 without Content-Range and an inside-the-document 416 place nothing), checked against the true document the control fetches whole; and the self-describing lines classify a corrupt file by shape (duplicated-prefix, shifted, short, mixed-generation, suffix-misplaced, other). `outcome` describes the file and the exit — complete (resumed / restarted / restarted-after-range / fresh), refused (partial untouched, error reported), corrupt (shape), incomplete-reported, harness-timeout, request-failed — and `outcome_vs_reference` says whether the client's file is what the reference placement yields. RFC 9110 defines what a 206 means and no resume algorithm, so a client that restarts on a 200 and one that stops with an error are both doing something the specification allows; the word "verdict" stays banned and the smoke verdict-word list now applies to this family too.
- **Roster (fixed by the survey; versions on every row):** curl 8.7.1 `-C -`, wget 1.25.0 `-c`, wget2 2.3.0 `-c`, HTTPie 3.2.4 `--download --continue`, huggingface_hub 2.2.0 `http_get(resume_size=)`, yt-dlp 2026.8.19 `--continue`, node-downloader-helper 2.1.11 `resumeIfFileExists`, nugget 2.2.0 `-c`, grab v3.0.1, go-getter v1.8.10 — ten clients whose own code decides to send a Range from the partial file's size. - **Grid:** 15 cells per client — fourteen flavors × one resume (a fresh directory holding the first 400 bytes of the 1,000-byte document, the client told to resume it) plus `always-206` × `fresh` (no partial: the flavor's lie is a 206 to a request that sent no Range, which a resumer never sends; `suffix-as-prefix`'s lie is likewise untriggered by a resume and the row says so); control rows: a `document` row (the true bytes), a `resume-raw` row per flavor, a `fresh-raw` row at always-206. Per-row cap 30 s, one client at a time, 1 s between rows; a response without `x-badhttp-version` is the rate limit, not an observation (wipe, 12 s, retry ≤ 3; a row that never clears has zero exchanges). The recorder's keep-alive is 60 s, above the cap, because on `off-by-one` and `shifted` wget waits for the 600th byte a Content-Range promised and a 599-byte body never carried, and that must be a deterministic timeout, not a race with the recorder's idle close.
