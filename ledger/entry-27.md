Seven real SSE client libraries plus a raw-wire control × 14 flavors = **112 rows** (98 client rows, 14 control rows), `family: "sse"`, all 112 landed on attempt 1 with `x-badhttp-version 0.21.0`, 0 retries, 0 harness timeouts. Roster, with the class each row carries: `eventsource`-interface libraries that reconnect by themselves — Node 26.10's built-in `EventSource` (undici 8.10.2, behind `--experimental-eventsource`), npm `eventsource` 5.1.2, `aiohttp-sse-client` 0.2.1, Go `tmaxmax/go-sse` v0.11.0 — and `one-shot` libraries that iterate one response — `httpx-sse` 0.4.3, `sseclient-py` 1.9.0, Go `r3labs/sse/v2` v2.10.0 (under `StopBackOff`); curl 8.7.1 as the control. **This is the first family whose oracle is a client-side specification, and it is derived from the wire rather than typed:** the control captures each flavor's body bytes and `scripts/witness-parse-sse.mjs` runs a reference implementation of WHATWG HTML §9.2.6 over them (unit-tested against every flavor's byte shape, plus id-persistence, the id-only block and the non-digit retry); every client row's `outcome` is a description relative to that parse and to the library's class, `diff` names the first difference, and the two classes are never compared with each other. The generator refuses a capture whose control does not reproduce what `src/sse.js` emits (floors: 5/1/1/1 events on ok/cut/drop/big, last id string 1 with buffer 2 and pending data on cut, exit 18 on drop, 65,536 data bytes on big), a partial grid, a row without the version on its first connection, a machine path, a foreign host or a verdict word.

**What the seven libraries did on 2026-10-05 (every claim is a row; the fourteen findings on `/sse` and `/clients` are computed from them).** 89 of 98 client rows match the reference parse and ended as expected for their class. The nine that differ, every one a real property of a library: `sseclient-py` and `r3labs/sse` deliver `cut`'s unterminated partial as an event (the spec discards it); `sseclient-py` delivers nothing at all on `drop` — urllib3 raises before handing back the 53 bytes that arrived — while `r3labs/sse` delivers the half-written second event as an empty event; `aiohttp-sse-client` splits on LF only, so a bare-CR stream yields **zero events**, and it strips every leading space, so `data:  foo` becomes `foo`; **both Go libraries fail the 65,536-byte line** — `bufio.Scanner`'s default 64 KiB token limit — delivering nothing of it; and `go-sse` returns from `comments` without an error and without scheduling a reconnect, because that stream happens to end on a bare comment line and its read loop treats that ending as a normal return, which its documentation does not describe. Everything else agreed with the reference: all seven reassembled the split UTF-8 characters, delivered `crlf` with clean values, joined `multiline` as the spec says, and delivered the named `error` event as an event — for the two Node libraries on the same listener a transport failure uses, so a caller has to look for the event's data to tell them apart. `wrong-type`: five refused it, `sseclient-py` and `r3labs/sse` delivered the three events (a one-shot library is under no obligation to check). `resume`: all four reconnecting libraries ran the sequence — three connections, Last-Event-ID 3 then 6, stopped at the 204 — and go-sse stops only because its validator rejects the 204 as a permanent failure. Three libraries (`go-sse`, `httpx-sse`, `r3labs/sse`) dispatch an empty event for the opening `retry: 30000` block, which the spec dispatches nothing for; those events are kept on the rows, marked `preamble`, and excluded from the comparison so one cause does not hide every other difference — and the finding names them.

**Two corrections this build made to this project's own text, both found by reviewers reading the algorithm rather than my paraphrase of it.** (1) Two of the three harness authors, independently, flagged the parser's and the site's claim that the Last-Event-ID is set "the moment the `id: 2` line is read": §9.2.6 sets the last event ID *buffer* then, but the *string* a reconnect sends is updated only when a blank line is processed (before the empty-data check), so after `cut`'s unterminated event a reconnect carries `1`, not `2`. Parser, test, finding, smoke pin and spec corrected before anything shipped. (2) The control harness as first written used `curl --raw`, which keeps the HTTP/1.1 chunk framing in the body; the reference parse of those bytes saw chunk-size lines and a trailing `0` chunk's blank line that dispatched `cut`'s partial, and **the parser's floor check refused the capture** ("reference for cut has 2 events, src/sse.js emits 1"). The flag was removed and the whole 112-row capture re-run (#23's rule: whole, never spliced), 20 minutes.
