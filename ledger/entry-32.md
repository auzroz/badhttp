- **Method, the part that is new.** Alignment of wire exchanges to fetches is exact by construction: the driver is a long-lived process; the orchestrator sends one `FETCH`, waits for its `RESULT`, lets the recorder settle 300 ms, and attributes every exchange that appeared since the previous `RESULT` to that fetch. That one protocol drives library caches (hishel, requests-cache, CacheControl, undici, make-fetch-happen, got, gregjones/httpcache), command-line conditional clients (`curl --etag-compare/--etag-save`, `curl -z`, `wget -N`) and caching proxies (nginx, Varnish, Squid, Apache Traffic Server — started per cell with the recorder as upstream and curl as their user) alike. The reference per flavor is derived from two curl control rows — `cold-raw` (no conditionals) and `revalidate-raw` (the textbook validation of RFC 9111 §4.3.1: `If-None-Match` and `If-Modified-Since` with the values cold-raw received, verbatim) — plus `revalidate-adopted-raw` on `mismatch` (the tag the 304 carried): a 304 → `document/stored-after-304` (reuse the stored response; the 304's validators select which stored response to update, so a different or missing ETag updates nothing and the textbook cache sends the same tag again), a 200 → `document/fresh-200`, a cold 304 → `undefined` (RFC 9110 defines 304 only for a conditional request). Each fetch is described by what went on the wire (`conditional`: none / etag / date / both; `etag_echo`: verbatim, weak-stripped, quotes-added…, `other` for a tag no 200 carried; `date_echo`: verbatim, reformatted, own-clock, invalid-echoed) and what the caller got (`document` via fresh-200 / stored-after-304 / no-request / stored-despite-200; `empty-304`; `other-status`; `error`); the row's `outcome` is the warm fetch's description; `adopted_304_validator` says whether a later fetch sent a tag the client only ever received in a 304. RFC 9111 §5.2.2.4 forbids reusing a no-cache response without validation and does not forbid an unconditional refetch, so `differs` is a description; the verdict-word ban list applies.

(c) *always-304* (a 304 to the very first, unconditional request): eleven clients passed the 304 to the caller empty and stored nothing; **got + cacheable-request and gregjones/httpcache stored the cold 304** (http-cache-semantics gives a response without a status property the status 200; httpcache stores anything not marked no-store) and revalidated it on fetches 2 and 3 with the tag it carried, handing the caller a 304 each time; wget `-N` exited 8 ("ERROR 304"); Varnish 503. (d) *no-validator-304* (a bare 304): seven kept their stored validators and sent both again; Traffic Server lost its stored ETag (it deletes the cached ETag unless the 304 carries one) and sent If-Modified-Since alone on fetch 3; got and undici deleted the entry. (e) *weak*: Traffic Server **stripped the `W/`** and sent a strong-looking tag; Squid and undici sent If-Modified-Since alone (Squid revalidates only with a strong quoted ETag; undici treats a bare token as unusable but keeps W/ tags — so on *unquoted* it, too, sent the date alone, as did Squid); everyone else echoed `W/"e-badhttp-1"` verbatim. (f) *bad-date* (an ISO 8601 Last-Modified): **five clients echoed the invalid string verbatim and got the 304 only an exact echo earns** — hishel, requests-cache, make-fetch-happen, got, gregjones/httpcache (none of them parses the date before sending it); four sent a date from a clock (curl `-z` from the file's mtime, wget `-N` from the download time, Squid and undici from the response's Date) and got 200; five sent no If-Modified-Since at all (CacheControl, nginx, Traffic Server, Varnish — and curl `--etag-compare`, which has no date code) — CacheControl because it stores only a response that carries an ETag (or max-age/Expires), so *bad-date* and *future* were never stored and all three of its fetches were unconditional; nginx and Traffic Server because an unparseable Last-Modified is not sent. (g) *future*: nine echoed the 2027 date and got 304; undici stored nothing (its freshness calculation returns early for a Last-Modified in the future); CacheControl as above. (h) *ignore* and the **stored-despite-200** rows: `curl -z` on *ignore* and *bad-date*, and `wget -N` on *ignore*, received a 200 with a body and kept their old file, reporting 304 to the caller — libcurl re-checks its time condition against the response and "simulates" a 304 when the Last-Modified is not newer or does not parse; wget drops a 200 whose Last-Modified is not newer and whose Content-Length matches the file as "Server ignored If-Modified-Since". (i) **`curl --etag-compare` sends `If-None-Match: ""` on every cold fetch and after every 304**: with a missing or empty compare file curl 8.7.1 sends the literal empty tag, and `--etag-save` truncates its file before the transfer and writes a tag only for a 2xx, so a 304 empties it — the pattern on ok, weak, mismatch, no-validator-304 and unquoted is 200, 304, 200. (j) Squid adds `Cache-Control: max-age=259200` (its default refresh_pattern's largest freshness) to every request it forwards, the cold one included. **The single most useful result: under `no-cache`, thirteen of fourteen clients revalidated and one (Varnish) never stored; of the thirteen, the validators went back verbatim from eight, stripped or filtered from three (Traffic Server's `W/`, Squid's and undici's refusal of a bare or weak tag), and rebuilt from a clock by four; and a 304 that lies about its ETag is believed by six of fourteen.**
