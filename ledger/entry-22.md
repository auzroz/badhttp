**Build decision: the family #20 and #21 both recommended — with its premise corrected before a line was written.** Both prior sessions argued for the cross-host redirect credential-boundary family on the grounds that *you cannot test whether an agent framework revalidates each redirect hop from a listener on 127.0.0.1, because the SSRF filter under test rejects it at hop zero.* **That half is true and it is the whole justification.** The other half — the implication that nobody hosts such a fixture — **is not**, and the research found it out: `httpbin.org` redirects to `eu.httpbin.org` (a real subdomain, real DNS, real TLS) and to `httpbingo.org` (a different registrable domain) today, through httpbin's `/redirect-to?url=` **open redirect**, which the maintained reimplementation `go-httpbin` has already closed with an allowlist. A researcher can and does build this by hand. **The real gap is narrower and still worth filling:** those chains exist by accident, depend on an open redirect that is being closed, are documented nowhere as credential fixtures, sit on a codebase whose last commit was 2018, and carry no expected-behaviour statement and no machine-readable corpus. That is what this family is, and the site claims nothing more.

**The budget question, answered by measurement rather than by preference.** The open design question was whether a *subdomain* is a real credential boundary or whether the family needed a second registered domain (~$11/yr against $0.01 of lifetime earnings). Reading twelve clients' source and then measuring eight of them live: **a subdomain is a boundary for nearly all of them, and Go net/http is the exception — by documented design.** `shouldCopyHeaderOnRedirect()` forwards Go's sensitive headers when the destination is the initial host *or a subdomain of it*, and the doc comment says so outright. **So the free subdomain is not a compromise, it is the better fixture: a second apex domain would show every client stripping and split nothing.** No domain was bought. `wrangler.jsonc` gained one line; the zone's universal certificate already covered `*.badhttp.dev`; the zone is on the Free plan at $0 and custom domains are not a billed unit (100 per zone; this zone now uses 2).

**Built (v0.17.0): `/crosshost`, nine flavors across two hosts.** `badhttp.dev` and `alt.badhttp.dev`, one Worker. `same-origin` (the control), `to-subdomain` (the flagship), `from-subdomain` (the same boundary reversed — it starts on the alt host), `boomerang` (out and back, ending where it began), `port-change` (`badhttp.dev` → `badhttp.dev:8443`, which Cloudflare serves for this zone under the same certificate), `relative-authority` (a protocol-relative `Location: //alt.badhttp.dev/…`, RFC 3986 §4.2, held as an exact constant), `scheme-upgrade` and `scheme-downgrade` (http↔https on one host; `always_use_https` is off and no HSTS header is sent, so both directions are buildable), and `jar` (host-only, `Domain=`-scoped and `__Host-` cookies planted before crossing). `/crosshost/land` is the oracle, served on both hosts, and reports what arrived.

**Three invariants the family is built on, all of them load-bearing.**
- **No open redirect, by construction.** No byte a caller sends reaches a `Location`. Targets are complete absolute URLs in a frozen `TARGETS` table selected by flavor name via `Object.hasOwn`, and every one is checked against `LOCATION_OK` before it is emitted, failing closed to a 500 rather than sending an unrecognized target. The single protocol-relative value is admitted by **exact string equality**, never by pattern, because a regex that admits the `//host` shape at all is one mistake from admitting `//evil.example`. There is no `?url=`, `?next=` or `?to=`, and smoke asserts that adding all three to a flavor URL changes nothing.
- **No echo, ever.** This family exists to be sent credentials by people testing whether their client leaks them, so some of those will be real ones sent by mistake. Nothing that arrives is reflected — not whole, not truncated, and **deliberately not hashed**, because a digest of a weak credential is a cracking target rather than a mitigation. The observables are presence, a scheme name only when it is Basic/Bearer/Digest (so a bare secret sent as an entire header value never has its first token reflected as a "scheme"), and a byte length. Cookie names are listed only for cookies badhttp itself minted. A credential that is not one of the published fakes gets a warning telling the caller to rotate it.
- **The alt host is a fixture, not a second site.** It serves `/crosshost`, its own `robots.txt` (`Disallow: /`) and `/health`, 404s everything else with a pointer home, and carries `X-Robots-Tag: noindex` on **every** response.

**Witnessed live against eight real clients (2026-09-10): 64 observations, zero errors.** curl 8.7.1, Go 1.27 net/http, Node 26 fetch, python urllib 3.14 (stdlib), requests 2.34.2, httpx 0.28.1, urllib3 2.7.0, aiohttp 3.14.3. The results are published in the `/crosshost` index under `witness`, dated, and worded as descriptions of what a caller received rather than verdicts on named libraries (the #19 rule).
- **`X-Api-Key` arrived intact in all 64.** Every one of these clients protects exactly three header names; the API-key convention most services actually use is not among them, so it crosses every boundary in the family. This is the most useful thing the table says and no flavor had to be built for it — it falls out of reporting a fourth header on every hop.
- **Go forwarded `Authorization` and `Cookie` across every boundary except subdomain→apex**, including the port change (it compares `URL.Hostname()`, which strips the port) and **including https→http, putting a credential on the wire in cleartext** while the landing response records `transport_was_encrypted: false`. Nothing is malfunctioning: the comparison Go documents is a hostname comparison, and neither a port nor a scheme changes the hostname.
- **python urllib (stdlib) forwarded both on all eight flavors** — its `HTTPRedirectHandler` copies caller-set headers with no host comparison of any kind. Credentials its own auth handlers generate live in a separate store that is not copied, so this bites headers the caller set, which is the common case for an API client.
- **curl restored both headers on `boomerang`**: it compares each hop against the *original* origin and regenerates rather than carrying a mutated map, so a chain that leaves badhttp.dev and returns arrives with what it dropped in between. Every other client that stripped stayed stripped.
- **requests and httpx kept `Authorization` on `scheme-upgrade`** where urllib3 and aiohttp stripped it — a carve-out both projects' source comments call backwards compatibility — and **both drop an explicitly-set `Cookie` on every redirect, the same-origin control included.**
- `boomerang` ends "present" for both curl and Go for *opposite reasons*, which is exactly why the directional pair exists: only `from-subdomain` separates "dropped and regenerated" from "never dropped".

**A citation correction that matters, because this ledger has carried it twice.** #20 and #21 both cite *"curl CVE-2026-11856, June 2026, leaking Digest auth state across hosts for twenty years of releases"* as motivating evidence. **The CVE is real — and it is not a redirect bug.** It is triggered by reusing one libcurl easy handle for a second transfer to a different origin, and curl's own advisory states the command-line tool is unaffected; no redirect fixture can reproduce it. Its sibling CVE-2026-7168 is the same defect on `Proxy-Authorization`. Neither is cited on the site, and `/crosshost` says plainly which advisories it *cannot* reproduce. The redirect-triggered advisories are plentiful and real, and they are what the family cites instead: CVE-2018-1000007, **CVE-2022-27776** (curl 4.9–7.82.0 — `Authorization` *and* `Cookie` leaked to the same hostname on a different port or scheme, the exact boundary `port-change` and the two scheme flavors test, unfixed for 22 years), CVE-2022-27774, CVE-2024-11053, CVE-2026-3783, CVE-2018-20060 (urllib3, whose definition of cross-origin is host, **port or scheme**), CVE-2023-32681 (requests, Proxy-Authorization), and CVE-2022-0235 / CVE-2022-0155 (node-fetch and follow-redirects, whose fixes added the same one-way subdomain carve-out Go documents).

**Four traps, and two of them are new.**
1. **Do not `dig` a hostname you are about to create.** The zone's SOA minimum is 1800 s, so the NXDOMAIN answer to a pre-creation query is negative-cached for half an hour — and **every subsequent lookup while it is cached renews it**, so polling to see whether it has cleared is what keeps it from clearing. `alt.badhttp.dev` resolved on 1.1.1.1 and the authoritative servers within seconds and stayed invisible to this machine for the rest of the session. The workaround that does not weaken anything: a `.curlrc` under `CURL_HOME` carrying `resolve = host:443:ip`, which injects the override into every curl in the smoke suite without editing the suite, plus a `getaddrinfo` shim for Python and a `DialContext` for Go. **The suite itself was left correct** — it relies on real DNS, as it should.
2. **The backtick trap bit inside a workflow script, not `page.js`.** The `/loop`-style prose in a `Workflow` script is itself a JS template literal; an unescaped backtick failed the launch. Same rule, wider blast radius than #19 recorded: escape every backtick in any prose that lives inside a template literal, wherever it lives.
3. **Two of this project's own suites against one IP will rate-limit each other, and the failure looks like a broken deploy.** A witness run started while a smoke run was still going produced 60+ FAILs, all of them `error code: 1015`. Three `smoke.sh` processes were alive at once because backgrounded runs were never confirmed finished. **Check `ps` before blaming the code**, and run exactly one suite at a time. This is #20's lesson generalized from corpus-assert to everything.
4. **A safety check can pass vacuously and prove nothing.** The no-echo assertion — the most important check in this family — sent sentinel credentials through `to-subdomain` and asserted none came back. It passed, because **curl correctly strips them at that boundary, so nothing ever arrived to be echoed.** It now runs through `same-origin` (the one boundary curl preserves) and a companion check asserts all four credentials **did** arrive before the no-echo assertion runs. #20's non-vacuity rule, learned again on the check that most needed it.

**Two bugs in this session's own code, both caught before the final deploy.**
- **A lying field.** `matches_documented_test_credential` OR'd three credentials into one boolean, so sending only the documented `X-Api-Key` while `Authorization` was stripped at the boundary reported `true` — a field saying something untrue about its own response, on the endpoint whose entire job is to report truthfully what arrived. It is now per credential, with `null` for "did not arrive, so nothing is claimed", and `chk chmatchshape` pins the shape rather than a value.
- **The alt host's 200 responses were indexable.** `X-Robots-Tag: noindex` was set on the not-found branch only, leaving the fixture pages — the ones a crawler following a documented redirect actually lands on — without it. Now applied to every response from that host, and smoke checks the 200s, not just the 404.
